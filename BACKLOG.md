# Backlog

Ordered roughly by priority. Items marked *(UX polish, 2026-07-28)* were ruled out of scope by the UX polish and accessibility design and are recorded here with its reasoning; *(spec §11)* are the roadmap items deferred from the original design.

1. **Finish the release-date curation.** *(curated dates, 2026-07-30)* Every shoe still sourced `listing` carries a year and nothing more, and every one of them can cross a recency-chip boundary, because the listing year runs late and never early (docs/scraping.md §Curated release months). A minority of those still have an indexed review and are cheap; the rest have none, and are budget models, GTX/GTS variants and brands with no English coverage, so no further publisher sitemap will reach them. How many are left, the runbook, the publisher yields and the tested Wayback CDX lead are all docs/operations.md §Resuming release-date curation. Also worth a pass: the curated rows marked `suspect` may have the month off by one — acceptable to ship, cheap to improve if a better source turns up.
2. **Method era: say when a reading is being retired.** *(UX polish, 2026-07-28)* Coverage is era-shaped, and the evidence is in docs/app.md §Coverage: every sparse metric is either arriving or retiring, never uniformly thin. "This test is being retired" is the one thing worth saying about a thin column, and the one thing the dataset cannot currently support — there is no notion of era per test, only the `previousId`/`updateId` links for pairs that were formally superseded (docs/scraping.md §Test lineage). Needs the dataset to carry it. Do not approximate it from the age of the oldest reading; that is precisely what the deleted sparse warning got wrong.
3. **Explain each metric where it is filtered.** *(curated-list review, 2026-07-30)* A sidebar row is a name, its units, a direction mark and a coverage count, and for several metrics that is still not enough to filter with. **The direction half is done**: every sidebar metric row now carries the two pickers' `↑`/`↓` under one legend, so `Outsole durability (mm)` says lower is better where the bound is typed and no longer contradicts the phone header's `Outsole wear` (docs/app.md §Table presentation). What is left is the sentence — **what the test measures**. `Outsole durability` is still the sharp case, because the mark says which end without saying that the reading is Dremel dent depth; `Drop`, `Torsional rigidity`, `Stiffness` and `Heel counter stiffness` have the same gap more mildly, and every `neutral` metric has it by construction: there is no better end, which is itself the thing worth saying and is exactly what a bare absent mark cannot say (docs/app.md §Theming). The mechanism this item was written against **no longer exists**: `HelpPopover` — one click-triggered popover on every device, anchored above 700px and a bottom sheet below, with focus return and Escape — was deleted with its last consumer when the chrome rebuild moved every word of explanation into one About panel (docs/app.md §The About panel). It would be recovered from git history rather than written again, and whoever does that should first ask whether fifty per-metric popovers are still the right shape now that the app has a single explanatory surface. Three things to settle either way: **where the copy lives** — one home per metric, beside `direction.ts` and `labels.ts` which already own per-metric facts, never inline in a component; **what it may claim** — this is RunRepeat's lab method being described, so a description states what the test measures and which end is better, and must not invent methodology we have not read (docs/decisions.md §Be a good citizen toward RunRepeat); and **how far it reaches** — the sidebar is where it matters most, but the column picker and the table headers want the same sentence, so it should be looked up by test slug rather than attached to a row. Roughly fifty metrics need a line each, which is the real cost.
4. **Cut what a drag re-renders, not just what it recomputes.** *(drag profiling, 2026-07-31; population half landed 2026-08-02)* What remains of a held grip's per-frame cost on the real fleet at desktop width splits about evenly between script with no hotspot in it — Svelte's own signal reads and DOM updates — and style recalculation. The table is the cause of both: it renders every visible row, up to the whole fleet, and rewrites a `--a` custom property per cell each frame because the wash ranks over the rendered rows. **Virtualising the table body is the real answer** and is a bigger change than it sounds: the pinned `thead`, the expanded row and the skip-link anchor all assume every row is in the DOM (docs/app.md §Columns and sorting), and find-in-page stops reaching rows that are not. Coalescing view updates to one per animation frame is the cheap alternative and was measured to buy nothing — Chromium and Firefox both already deliver about one `pointermove` per frame. The cheap half is done: `population.ts` holds the coverage population's identity while a range moves, so the sidebar's headings and the brand counts no longer re-walk the fleet per frame; the per-row `excluded` counts correctly stay per-frame, being leave-one-out reads over the live filters rather than of `considered` (docs/app.md §What a drag may recompute).
5. **Open Graph tags.** *(UX polish, 2026-07-28)* The page has a title and a favicon, so a shared link previews as *something* (docs/app.md §Sharing is copying the address bar), but there are no `og:`/`twitter:` tags and therefore no card. Deferred rather than done because it needs an image, and an image needs a decision about what this tool looks like — a screenshot dates, and there is no logo.
6. **A first-shoe story.** *(score analysis, 2026-07-30)* "What single shoe should I buy" is the question a new runner actually asks, and no combination of the three answers it — the measurements are in docs/shoe-stories.md §No composite over the three stories, and the failure is that a composite ranks *bouncy and light*: its top 20 is mostly carbon at a median price well above the fleet's, while the mainstream cushioned and stability trainers a beginner is usually pointed at sit in the bottom third. The gap is a story rather than a statistic, so it arrives as a fourth `ScoreDef` (docs/app.md §The story scores) built on terms the three under-use — stack, midsole width, heel counter, outsole life — and deliberately not on energy return. Two things it must settle before any weight is chosen: the pool its frozen constants are derived over (docs/decisions.md §Frozen scores and live thresholds), for which *in production and unplated* is the candidate, and how it survives the honesty limit that fit, upper and comfort are most of what makes a first shoe good and the fleet measures none of them — so it must not claim to rank "best". Worth knowing first: the useful list this was reaching for already exists without a new score, as the plain filters *unplated, at or below the fleet's median price, in production* over any of the three columns — read the median off the price filter rather than hard-coding one, since it moves with every refresh.

8. **A `zone=` shorthand in the URL.** *(doc-promised, recorded 2026-08-03)* docs/app.md §URL encoding says this item is here, and the categorical-filters sweep found that it was not — it is written down so the promise is true, which is the whole reason it sits at this priority. The zone rides in `cols` because one encoding of it cannot disagree with itself, so a plain forefoot table is a verbose link: eight column slugs where `zone=forefoot` would be one. The remedy is a token expanding to `defaultColumns(zone)` on parse, written only when the columns are exactly that zone's default — which leaves two spellings of one view in circulation, and the app is mostly indifferent to that, since `isDefaultView`, `All`'s mark and `upToColumnOrder` all compare view objects rather than query strings. The thing to settle before writing it is what an old link carrying the shorthand should mean once `defaultColumns` next changes: expanding it against the new defaults silently shows a different table from the one the sender saw, and refusing it drops the zone altogether. Contingent either way — it is the remedy for a link length nobody has complained about yet.
9. **One home for the disclosure and the segmented control.** *(categorical filters review, 2026-08-02)* `FeaturesFilter` carries `BrandFilter`'s `summary`, chevron and `li` styling verbatim, and `DiscontinuedFilter`'s `.disc` verbatim as `.tri` — **including both WHY comments**, so a theming decision argued once now lives in three files. The spec sanctioned the *shapes*; nothing sanctioned three copies, and this codebase already carries that scar (`PLATE_LABELS` exists because three copies of the word "None" drifted, docs/app.md §Categorical columns). It is not a fix-wave edit: extracting a disclosure primitive and a segmented-control primitive is a design task that needs its own render evidence at both widths and in both themes, and doing it badly is worse than the duplication. **Two triggers say when it stops being deferrable** — the next change to the accent tokens, and the next change to the focus-ring rule (docs/app.md §Theming). Either one will otherwise be made in one file and missed in two.
10. **Why the feature filters use button-radios, written down truthfully.** *(facet headings review, 2026-08-03)* `DiscontinuedFilter.svelte` and `app/e2e/features.spec.ts` each justify buttons carrying `role="radio"` over native `input[type=radio]` on the grounds that two rendered copies of the sidebar must not join one document-wide group by sharing a `name`. There are not two copies and there never were: `Page.svelte` mounts `FilterSidebar` once and the drawer is that same element moved off-canvas by a class (docs/app.md §Filters), and `git log -S'<FilterSidebar'` returns a single commit. A third copy of that fiction was deleted when the facets gained headings; these two were left standing because the decision is right for reasons nobody wrote down — `use:roving` needs a roving-tabindex group the browser does not own, `Any` is an unsettable state a native radio cannot express without a fourth input, and the segmented face is shared with the tri-states. Which of those is *the* reason, and whether it belongs in a comment or in docs/app.md §Filters now that it shapes three sites, is the thing to settle; that is a design call, not a comment edit. Worth doing alongside *One home for the disclosure and the segmented control* — same components, same paragraph.
11. **Gate the shape of a test slug where the catalogue is written.** *(facet headings review, 2026-08-03)* A facet group now takes its accessible name from its own heading through `aria-labelledby="facet-{test.slug}"`, which makes the slug an HTML id — and `aria-labelledby` is an ID-*reference list*, so an upstream slug carrying a space would reference two ids that do not exist and the group would lose its name silently, with nothing failing. `scraper/src/test-catalogue.ts` takes the slug straight from the payload and validates nothing about its characters. What shipped is an app-suite assertion over the committed `data/tests.json` (`FeaturesFilter.test.ts`), which fails the build but only after a refresh has already published the bad slug. The stronger form is the one this project's own rule asks for — a gate that refuses to *write* it (docs/scraping.md §Validation gates) — and it belongs beside the duplicate-id and duplicate-slug checks in `indexCatalogue`, one more comparison in a loop that already walks every test. Held out of that change only because both branches were in flight at once. Two things found in the same review belong with it. **The check should fire before the crawl is spent**: `scrape-metrics-main.ts` extracts the catalogue and then makes one live request per numeric test before `indexCatalogue` ever sees it, so a malformed catalogue costs the whole polite crawl and only then fails — where the extractor's own 50-test floor deliberately fails before a single API call (docs/scraping.md §Validation gates, docs/policies.md §Third parties and cost). And **the app-side stopgap is stricter than the failure mode it names**: `ID_TOKEN` demands `[a-z0-9-]+` where the only thing `aria-labelledby` cannot survive is whitespace, so a benign upstream `heel_tab` would redden `verify` — and since a refresh pushes with `GITHUB_TOKEN` and dispatches the deploy directly, the app suite never runs on the refresh, so such a slug would deploy and then block the *next* CI run until someone loosened the regex. Failing loud beats failing silent, which is why it ships as it is, but it is a build gate on data nobody here controls.
