# Backlog

Ordered roughly by priority. Items marked *(final review)* came out of the pre-merge whole-branch review; *(UX polish, 2026-07-28)* were ruled out of scope by the UX polish and accessibility design and are recorded here with its reasoning; *(spec §11)* are the roadmap items deferred from the original design.

1. **Tune Tempo's and Race's thresholds against real use.** Easy no longer has thresholds to tune — it ranks (docs/app.md §The Easy score) — so this narrows to the two stories that still bound. Applied to the live fleet they return **Tempo 54 and Race 39 of 450**, and docs/shoe-stories.md describes Tempo as the widest of the three by intent, "where most weeks' hard running happens", so the narrowest but one is evidence against the thresholds rather than against the story. Tempo is the least settled for that reason: both its bounds are percentiles of the live fleet — weight at the 40th, energy return at the 50th — and each is a guess at what "light" and "lively" mean. Score any candidate change the way docs/shoe-stories.md §Checking a threshold set describes, remembering that the check is one-sided. The `pace` fact is one editor's label and never the filter (docs/scraping.md §Editorial facts).
2. **Surface imprecise release dates in the app.** *(usability review, 2026-07-28)* Only 24 of 450 shoes carry a real release date; the other 426 are stamped 1 January (docs/scraping.md §Release-year supplement). So the "2y" chip drops 119 of the 120 shoes released in 2024, and any date bound silently drops the 17 shoes with no date at all — while the receipt reports "0 outside your bounds", because its accounting covers range filters only. This is the honesty problem the tool exists to solve, in the one filter that does not participate in it. Either extend the receipt to non-range filters or mark imprecise dates in the table; ideally both. Note there is also no "released before" bound, so the last-generation strategy in docs/shoe-stories.md cannot be expressed at all.
3. **Per-column user-declared direction.** *(UX polish, 2026-07-28; partly superseded 2026-07-30)* Roughly thirty numeric metrics are `neutral` in `app/src/lib/direction.ts` — stack, drop, softness, stiffness, every width — because there is no fleet-wide better end, so they take the grey "more" ramp (docs/app.md §Theming). Easy's score has settled the part of this that is about a *story*: per-story direction is the score's business and fleet-wide direction stays `direction.ts`'s, so the metrics the score reads are asserted in one direction there while staying `neutral` in the table. What is left is the runner's own per-column preference. Deferred because it adds serialised view state and so changes what a shared link means — `stab=1` is now the precedent for that (docs/app.md §URL encoding), so the question is decidable rather than open.
   **A general metric picker for the score is rejected**, not deferred: most metrics have no defensible direction, so offering one would assert a better end the data does not support; swapping a well-covered term for a thin one *does* move the eligible set, so the list's length and composition would shift confusingly, where the stability pair is the lucky exception that cannot; and it means 2^N score variants to serialise, test and explain for what is one real preference.
4. **Method era: say when a reading is being retired.** *(UX polish, 2026-07-28)* Coverage is era-shaped, and the evidence is in docs/app.md §Coverage: every sparse metric is either arriving or retiring, never uniformly thin. "This test is being retired" is the one thing worth saying about a thin column, and the one thing the dataset cannot currently support — there is no notion of era per test, only the `previousId`/`updateId` links for pairs that were formally superseded (docs/scraping.md §Test lineage). Needs the dataset to carry it. Do not approximate it from the age of the oldest reading; that is precisely what the deleted sparse warning got wrong.
5. **CSV date-precision column.** *(final review)* `shoes.csv` and the in-app export emit year-derived dates with nothing marking them imprecise; add a `preciseReleaseDate` column (schema addition — semantics in docs/scraping.md §Release-year supplement). The export's `url` column has landed already (docs/app.md §Number display), so this is all that is left of the CSV work.
6. **Back/forward navigation, and row expansion in the URL.** `popstate` is unhandled, so Back doesn't restore the previous view. Must be worked through against docs/app.md §View and URL ownership rather than around it. Expanded rows belong to the same visit: putting them in the URL adds a field to `ViewState`, which must serialise, and an expanded row would then stop equalling `defaultView`, so the toolbar would drop its `All` mark because someone opened a row. Both are the same question about what a shared link means.
7. **Harvest the option-typed tests.** `tongue-gusset-type` and `heel-tab` are populated on nearly every shoe page but are never fetched, so they drop out as empty (docs/scraping.md §Empty tests). The details crawl already has the page; reading them there costs no requests. Needs a home for non-numeric per-shoe readings, which the app has no column type for today.
8. **Open Graph tags.** *(UX polish, 2026-07-28)* The page has a title and a favicon, so a shared link previews as *something* (docs/app.md §Sharing is copying the address bar), but there are no `og:`/`twitter:` tags and therefore no card. Deferred rather than done because it needs an image, and an image needs a decision about what this tool looks like — a screenshot dates, and there is no logo.
9. **A `side=` URL shorthand.** *(side-as-preset design, 2026-07-29)* The side is derived from the columns and has no token of its own (docs/app.md §URL encoding), so a plain forefoot table is a 119-character link of eight column slugs where `side=forefoot` would be one. That was the accepted cost of having a single encoding of the side rather than two that can disagree, and the shorthand would reintroduce the second one — `side=` would have to expand to `defaultColumns(side)` on parse and be written only when the columns are exactly that, or a link could say forefoot and show heel. Do it if a forefoot plain-table link's length becomes annoying in practice, not before.
10. **One-click return from a table with no measurements.** *(branch review, 2026-07-29)* Untick both Stack and Energy return in the column picker and the view names no side, so `All` clears the filters and leaves the columns alone (docs/app.md §What All does) — correctly marked, and correctly inert. Getting the plain table back then takes two clicks rather than one: a side click appends that side's two measurement columns at the *end*, where `defaultColumns` interleaves them, so the order differs, `All` goes unlit, and a second press restores it. Fixable by having `All` treat "uses neither half" as its own case rather than folding it in with "uses both", at the cost of a third branch in `allView` and a second reading of what `sideOf`'s `null` means. Not worth it unless someone actually strands themselves there.
11. **Tempo and Race on the same pipeline.** *(preset-scoring design, 2026-07-30)* Easy ranks by a lab-measurement score with frozen constants (docs/app.md §The Easy score); the two fast stories still bound and sort by a single metric. Same four stages, different terms and weights — and the terms want the same treatment Easy's got: a physical mapping per metric rather than a percentile, and a coverage check over the three-year window rather than fleet-wide (docs/shoe-stories.md §The shared rules). Each new score adds its own frozen constant set, including anchors per side and per any toggle it carries.
12. **Easy has lost the sparse-bound guard.** *(preset-scoring design, 2026-07-30)* `presets.test.ts` asserts that no preset bounds a metric whose coverage falls below `SPARSE_BELOW` (docs/app.md §Coverage), and the guard only looks at range keys — so a story that bounds nothing is trivially covered by it. The equivalent property for a score is that no *term* is thin, which nothing checks today; the toggle-invariant test is the only coverage assertion the score has.
13. **Head-to-head compare view.** *(spec §11)* Select 2–4 shoes for a side-by-side metric comparison.
14. **Other categories.** *(spec §11)* Trail/hiking/sneakers — the pipeline is parameterised by seed shoe already; needs a category switcher in the UI and per-category datasets. Each details record already carries the per-shoe `categorySlug` this would key on (docs/scraping.md §Non-running shoes), which currently only ever excludes.
15. **Price/deal tracking.** *(spec §11)* MSRP history is implicit in git history of `data/`; surface it.
16. **Public refresh trigger.** *(spec §11)* Currently refresh buttons need repo access; an issue-ops trigger would let friends request one.
