Ordered roughly by priority. Items marked *(UX polish, 2026-07-28)* were ruled out of scope by the UX polish and accessibility design and are recorded here with its reasoning; *(spec §11)* are the roadmap items deferred from the original design.

1. **Finish the release-date curation.** *(curated dates, 2026-07-30)* Every shoe still sourced `listing` carries a year and nothing more, and every one of them can cross a recency-shortcut boundary, because the listing year runs late and never early (docs/scraping.md §Curated release months). A minority of those still have an indexed review and are cheap; the rest have none, and are budget models, GTX/GTS variants and brands with no English coverage, so no further publisher sitemap will reach them. How many are left, the runbook, the publisher yields and the tested Wayback CDX lead are all docs/operations.md §Resuming release-date curation. Also worth a pass: the curated rows marked `suspect` may have the month off by one — acceptable to ship, cheap to improve if a better source turns up.
2. **Method era: say when a reading is being retired.** *(UX polish, 2026-07-28)* Coverage is era-shaped, and the evidence is in docs/app.md §Coverage: every sparse metric is either arriving or retiring, never uniformly thin. "This test is being retired" is the one thing worth saying about a thin column, and the one thing the dataset cannot currently support — there is no notion of era per test, only the `previousId`/`updateId` links for pairs that were formally superseded (docs/scraping.md §Test lineage). Needs the dataset to carry it. Do not approximate it from the age of the oldest reading; that is precisely what the deleted sparse warning got wrong.
3. **Explain each metric where it is filtered.** *(curated-list review, 2026-07-30)* A sidebar row is a name, its units, a direction mark and a coverage count, and for several metrics that is still not enough to filter with. **The direction half is done**: every sidebar metric row now carries the two pickers' `↑`/`↓` under one legend, so `Outsole durability (mm)` says lower is better where the bound is typed and no longer contradicts the phone header's `Outsole wear` (docs/app.md §Table presentation). What is left is the sentence — **what the test measures**. `Outsole durability` is still the sharp case, because the mark says which end without saying that the reading is Dremel dent depth; `Drop`, `Torsional rigidity`, `Stiffness` and `Heel counter stiffness` have the same gap more mildly, and every `neutral` metric has it by construction: there is no better end, which is itself the thing worth saying and is exactly what a bare absent mark cannot say (docs/app.md §Theming). The mechanism this item was written against **no longer exists**: `HelpPopover` — one click-triggered popover on every device, anchored above 700px and a bottom sheet below, with focus return and Escape — was deleted with its last consumer when the chrome rebuild moved every word of explanation into one About panel (docs/app.md §The About panel). It would be recovered from git history rather than written again, and whoever does that should first ask whether fifty per-metric popovers are still the right shape now that the app has a single explanatory surface. Three things to settle either way: **where the copy lives** — one home per metric, beside `direction.ts` and `labels.ts` which already own per-metric facts, never inline in a component; **what it may claim** — this is RunRepeat's lab method being described, so a description states what the test measures and which end is better, and must not invent methodology we have not read (docs/decisions.md §Be a good citizen toward RunRepeat); and **how far it reaches** — the sidebar is where it matters most, but the column picker and the table headers want the same sentence, so it should be looked up by test slug rather than attached to a row. Roughly fifty metrics need a line each, which is the real cost.

7. **Delete the phone table's column-count floor, once WebKit has been read.** *(url-shorthand review, 2026-08-04)* `ShoeTableMobile.svelte` floors its `colspan`/`--cols` value at 1 with `Math.max(cols.length, 1)`, and the zero-column view that became link-reachable on this branch is the only view that exercises it. Measured in Chromium and Firefox at 360px and 375px, built and served the way `npm run e2e` serves it, with the floor and without: **every rendered box is identical** — bleed, panel, table and identity cell, to the pixel, along with the row count and the document's scroll width. The floor changes exactly two things and neither reaches the screen. `colspan` goes from `"0"` to `"1"`, and HTML5 clamps `colspan="0"` to 1 — `colSpan` reflects 1 in both engines — only `rowspan` having kept HTML4's "every remaining cell" meaning, which is precisely the belief the component comment asserted for some time before this branch measured it. And the table's computed `min-width` goes from the bare border-spacing to one column's worth, which can never bind, because the table is `width: 100%` inside a bleed roughly six times wider at the narrowest layout this app supports (docs/app.md §The narrowest supported width is 360px). **The gap to close first is WebKit.** Use the Docker route in docs/operations.md §The e2e run needs three browsers. The clamping is near-certainly universal, but a compatibility floor of three engines is not a thing to delete on two. Run the same probe in the Playwright image at both widths, then delete the `Math.max` and the comment that now records all of this; the phone rendering of a zero-column view is asserted in `ShoeTableMobile.test.ts` as what a runner sees, so nothing should go red. Low priority and low risk: the line costs nothing where it stands, and its comment is already the useful half.
8. **Render a dropped slug's header breakable, and model it that way.** *(virtualising the table, 2026-08-04)* The width model never treats a hyphen as a break opportunity, so a column's header is its widest whitespace-delimited token — deliberate over-reservation, because all three engines break at *some* hyphens and no two agree which, and a rule tuned to either puts the model under another's min-content, which is a header hanging out of a declared column (docs/app.md §Table presentation). It is safe and it is right for every label the app writes; the whole price falls on a column named by a slug the catalogue no longer holds, which renders as the raw slug over em dashes (docs/app.md §Columns are permissive, ranges and sorts are strict). Measured against `main` at 1440px, the worst slug today's catalogue can be asked for takes its column from 566px to 790px, and the ceiling over every slug the URL parser accepts is **691px of surplus header**, pinned in `app/src/lib/fit.test.ts` against both of the constants it is derived from. The remedy is to render a dropped slug's header breakable and model it as breakable, rather than to reason about break rules again: `columnLabel` and `wordsOf` both change, the break opportunities have to be measured in three engines rather than named from a standard — three attempts to name them from one were all wrong — a zero entry is needed in all three font tables for whatever character the break is drawn with, and the 691px pin is re-priced rather than deleted. Model and render have to land together, since a declared width the render disagrees with is the failure this guards. **Not urgent**: a dropped slug is already a degraded rendering, and what it costs is a stale link being handed the stacked list at a width the desktop table would have fitted.
