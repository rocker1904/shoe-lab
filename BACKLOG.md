# Backlog

Ordered roughly by priority. Items marked *(final review)* came out of the pre-merge whole-branch review; *(UX polish, 2026-07-28)* were ruled out of scope by the UX polish and accessibility design and are recorded here with its reasoning; *(spec §11)* are the roadmap items deferred from the original design.

1. **Finish the release-date curation.** *(curated dates, 2026-07-30)* Every shoe still sourced `listing` carries a year and nothing more, and every one of them can cross a recency-chip boundary, because the listing year runs late and never early (docs/scraping.md §Curated release months). A minority of those still have an indexed review and are cheap; the rest have none, and are budget models, GTX/GTS variants and brands with no English coverage, so no further publisher sitemap will reach them. How many are left, the runbook, the publisher yields and the tested Wayback CDX lead are all docs/operations.md §Resuming release-date curation. Also worth a pass: the curated rows marked `suspect` may have the month off by one — acceptable to ship, cheap to improve if a better source turns up.
2. **Per-column user-declared direction.** *(UX polish, 2026-07-28; partly superseded 2026-07-30)* Roughly thirty numeric metrics are `neutral` in `app/src/lib/direction.ts` — stack, drop, softness, stiffness, every width — because there is no fleet-wide better end, so they take the grey "more" ramp (docs/app.md §Theming). The story scores have settled the part of this that is about a *story*: per-story direction is a score's business and fleet-wide direction stays `direction.ts`'s, so the metrics the score reads are asserted in one direction there while staying `neutral` in the table. What is left is the runner's own per-column preference. Deferred because it adds serialised view state and so changes what a shared link means — `stab=1` is now the precedent for that (docs/app.md §URL encoding), so the question is decidable rather than open.
   **A general metric picker for the score is rejected**, not deferred: most metrics have no defensible direction, so offering one would assert a better end the data does not support; swapping a well-covered term for a thin one *does* move the eligible set, so the list's length and composition would shift confusingly, where the stability pair is the lucky exception that cannot; and it means 2^N score variants to serialise, test and explain for what is one real preference.
3. **Method era: say when a reading is being retired.** *(UX polish, 2026-07-28)* Coverage is era-shaped, and the evidence is in docs/app.md §Coverage: every sparse metric is either arriving or retiring, never uniformly thin. "This test is being retired" is the one thing worth saying about a thin column, and the one thing the dataset cannot currently support — there is no notion of era per test, only the `previousId`/`updateId` links for pairs that were formally superseded (docs/scraping.md §Test lineage). Needs the dataset to carry it. Do not approximate it from the age of the oldest reading; that is precisely what the deleted sparse warning got wrong.
4. **Explain each metric where it is filtered.** *(curated-list review, 2026-07-30)* A sidebar row is a name, its units, a direction mark and a coverage count, and for several metrics that is still not enough to filter with. **The direction half is done**: every sidebar metric row now carries the two pickers' `↑`/`↓` under one legend, so `Outsole durability (mm)` says lower is better where the bound is typed and no longer contradicts the phone header's `Outsole wear` (docs/app.md §Table presentation). What is left is the sentence — **what the test measures**. `Outsole durability` is still the sharp case, because the mark says which end without saying that the reading is Dremel dent depth; `Drop`, `Torsional rigidity`, `Stiffness` and `Heel counter stiffness` have the same gap more mildly, and every `neutral` metric has it by construction: there is no better end, which is itself the thing worth saying and is exactly what a bare absent mark cannot say (docs/app.md §Theming). The mechanism this item was written against **no longer exists**: `HelpPopover` — one click-triggered popover on every device, anchored above 700px and a bottom sheet below, with focus return and Escape — was deleted with its last consumer when the chrome rebuild moved every word of explanation into one About panel (docs/app.md §The About panel). It would be recovered from git history rather than written again, and whoever does that should first ask whether fifty per-metric popovers are still the right shape now that the app has a single explanatory surface. Three things to settle either way: **where the copy lives** — one home per metric, beside `direction.ts` and `labels.ts` which already own per-metric facts, never inline in a component; **what it may claim** — this is RunRepeat's lab method being described, so a description states what the test measures and which end is better, and must not invent methodology we have not read (docs/decisions.md §Be a good citizen toward RunRepeat); and **how far it reaches** — the sidebar is where it matters most, but the column picker and the table headers want the same sentence, so it should be looked up by test slug rather than attached to a row. Roughly fifty metrics need a line each, which is the real cost.
5. **Cut what a drag re-renders, not just what it recomputes.** *(drag profiling, 2026-07-31)* A held grip now costs about 20ms of main thread per frame on the 450-shoe fleet at desktop width, so a drag runs at roughly 45-50fps rather than 60; the reactivity half of that is done (docs/app.md §What a drag may recompute), and what is left splits about evenly between script with no hotspot in it — Svelte's own signal reads and DOM updates — and style recalculation. The table is the cause of both: it renders every visible row, up to the whole fleet, and rewrites a `--a` custom property per cell each frame because the wash ranks over the rendered rows. **Virtualising the table body is the real answer** and is a bigger change than it sounds: the pinned `thead`, the expanded row and the skip-link anchor all assume every row is in the DOM (docs/app.md §Columns and sorting), and find-in-page stops reaching rows that are not. Coalescing view updates to one per animation frame is the cheap alternative and was measured to buy nothing — Chromium and Firefox both already deliver about one `pointermove` per frame. Worth doing first, either way, because it is small: the sidebar's coverage headings and every row's `excluded` count are recomputed per frame although a **range** change cannot move `considered`, which is the population they read (docs/app.md §Coverage) — roughly a dozen fleet passes a frame that a reference-stable population would delete.
6. **A filter for the categorical columns.** *(categorical columns, 2026-07-30)* `tongue-gusset-type`, `heel-tab`, `removable-insole` and `reflective-elements` are readable and sortable columns now (docs/app.md §Categorical columns) but nothing filters them, so "show me shoes with a gusseted tongue" still cannot be asked. The shape is a set-membership facet like plate or brand rather than a range, but only for two of them: `tongue-gusset-type` and `heel-tab` are closed enums, while `removable-insole` and `reflective-elements` are booleans (docs/scraping.md §Readings taken from the page), so those two want a checkbox or a tri-state rather than a checklist. It wants `FilterState` to carry `Record<string, string[]>`, a serialisation, and the facet-counting rule brands already follow (docs/app.md §Filters). Deferred because the column earns its keep for side-by-side comparison without it, and because a fifth categorical source is pending: the editorial facts are detail-panel-only today and would want the same control.
7. **Open Graph tags.** *(UX polish, 2026-07-28)* The page has a title and a favicon, so a shared link previews as *something* (docs/app.md §Sharing is copying the address bar), but there are no `og:`/`twitter:` tags and therefore no card. Deferred rather than done because it needs an image, and an image needs a decision about what this tool looks like — a screenshot dates, and there is no logo.
8. **A `zone=` URL shorthand.** *(zone-as-preset design, 2026-07-29)* The zone is derived from the columns and has no token of its own (docs/app.md §URL encoding), so a plain forefoot table is a link spelling out eight column slugs where `zone=forefoot` would be one token. That was the accepted cost of having a single encoding of the zone rather than two that can disagree, and the shorthand would reintroduce the second one — `zone=` would have to expand to `defaultColumns(zone)` on parse and be written only when the columns are exactly that, or a link could say forefoot and show heel. Do it if a forefoot plain-table link's length becomes annoying in practice, not before.
9. **One-click return from a table with no measurements.** *(branch review, 2026-07-29)* Untick both Stack and Energy return in the column picker and the view names no zone, so `All` clears the filters and leaves the columns alone (docs/app.md §What All does) — correctly marked, and correctly inert. Getting the plain table back then takes two clicks rather than one: a zone click appends that zone's two measurement columns at the *end*, where `defaultColumns` interleaves them, so the order differs, `All` goes unlit, and a second press restores it. Fixable by having `All` treat "uses neither half" as its own case rather than folding it in with "uses both", at the cost of a third branch in `allView` and a second reading of what `zoneOf`'s `null` means. Not worth it unless someone actually strands themselves there.
10. **A first-shoe story.** *(score analysis, 2026-07-30)* "What single shoe should I buy" is the question a new runner actually asks, and no combination of the three answers it — the measurements are in docs/shoe-stories.md §No composite over the three stories, and the failure is that a composite ranks *bouncy and light*: its top 20 is mostly carbon at a median price well above the fleet's, while the mainstream cushioned and stability trainers a beginner is usually pointed at sit in the bottom third. The gap is a story rather than a statistic, so it arrives as a fourth `ScoreDef` (docs/app.md §The story scores) built on terms the three under-use — stack, midsole width, heel counter, outsole life — and deliberately not on energy return. Two things it must settle before any weight is chosen: the pool its frozen constants are derived over (docs/decisions.md §Frozen scores and live thresholds), for which *in production and unplated* is the candidate, and how it survives the honesty limit that fit, upper and comfort are most of what makes a first shoe good and the fleet measures none of them — so it must not claim to rank "best". Worth knowing first: the useful list this was reaching for already exists without a new score, as the plain filters *unplated, at or below the fleet's median price, in production* over any of the three columns — read the median off the price filter rather than hard-coding one, since it moves with every refresh.
11. **Bound the header's unit line, not just its name.** *(visual polish review, 2026-07-31)* `size-rating`'s units read `3 = true` (docs/app.md §Table presentation), which is eight characters of JetBrains Mono against the 53px column the phone gives six of them — measured at 360px it takes **two lines, 32px against every other column's 16px**, and it sets the pinned header's height in any view where no column name takes a third line. The label guard in `app/src/lib/labels.test.ts` cannot see it: `MAX_LABEL_PX` and `MAX_LABEL_LINES` are applied to `columnLabel`/`shortLabel` and nothing measures `headerUnits`, so a units string of any length ships silently. The fix is one more assertion over the same catalogue loop, and the real work is what it needs to measure against: `CHAR_PX` in `labels.ts` is generated for Inter Tight at 12px/600 by `app/scripts/measure-label-widths.mjs`, and the unit line is set in the figure face, so it wants a second table from the same script. Deferred because `size-rating` is the only units override and is not in the default set, so the cost today is a phone header 16px taller in a view that has opted into that column.
12. **Decide whether the add-filter dialog keeps its scrim.** *(polish review, 2026-07-31)* The dialog dims the page behind it, which is the elevation language applied — nothing else in the app floats above content without a scrim (docs/app.md §Filters) — but it is the only dim a runner meets at a desktop width — the drawer's is the same full-page element below 800px — in a tool whose loop is *change a bound, read the table*, and it ships on trial rather than settled. Deciding **against** it is three deletions: the `.scrim` element in `AddFilterDialog.svelte`, the four `.scrim` rules beside it, and the test naming `add-filter-scrim`. Nothing else reads any of them, `onclose` is the dialog's own prop, and both sites carry a `PROVISIONAL` comment saying exactly this. What must survive either way is the **outside-press dismissal** the scrim currently carries: every other floating panel has one, and dropping the element without replacing that leaves this the single modal you cannot click away from (docs/app.md §Every floating panel dismisses the same way). The row in the stacking table and the sentence in §Filters go with it.

16. **Retune the wash defaults so the top of the table separates.** *(display menu, 2026-08-02)* The current curve is tuned to work as well as it can across the whole range, and a buyer largely cares about the best shoes — the leaders do not pull apart enough. The **menu is now shipped** (docs/app.md §The display preferences): better hue and vividness, a base colour, strength, emphasis and the floor are all live controls with their numbers beside them, stored locally and guarded so no setting can drop the ink under 4.5:1. What is left is the retune itself, which is a *decision* rather than a build — sit with the real fleet, move the grips until the top ten separate, read the numbers off the panel and write them into `DISPLAY_DEFAULTS` in `app/src/lib/wash.ts`. Three things the engine already settles for whoever does it: the ramp's guard is a property test over a grid rather than the shipped constants, so new defaults cannot ship illegible; the painted strength is `min(strength, cap)` and the caps are generous at the default hue (0.966 light, 0.981 dark), so the room is in **emphasis and floor** rather than in strength; and the default state is the one state that writes no override at all, so changing these constants changes what `--wash-blue` means to the whole app rather than adding a layer — `tokenFill` in `resolveWash` keys off them, and moving them without moving `app.css`'s tokens together would make the two disagree about what "default" paints. Worth trying first, measured on the real fleet: emphasis past 2.5 with the floor around 0.4, which is what the podium reading of this item actually asks for.
